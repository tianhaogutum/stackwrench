# stackwrench devcontainer

`stackwrench devcontainer` (formerly `devcontainer-wirecheck`) runs offline wiring
checks across a Dev Container definition, a Compose model and a local Linux
workspace. It produces a graph connecting service references, build inputs, bind
sources, named volumes and workspace coverage, with source locations. Useful before
opening a container, and in CI for catching renamed services, missing bind
directories and Dockerfile paths resolved from the wrong directory.

This is an independent, narrow static checker, not a Dev Container or Compose
runtime, general schema validator, security audit, or guarantee that a container
will start. It never runs lifecycle commands, environment probes, Docker, shells,
or network calls. It does not create missing paths. No credentials are needed.

This command is a Python port of the original Node.js tool; output formats, rule
IDs and exit codes are unchanged. The few places where it cannot behave
identically are listed in [Known divergences from the Node.js
implementation](devcontainer-port.md).

## Install

Requires Linux and Python 3.11 or newer. The only runtime dependency is PyYAML.

```sh
pipx install stackwrench                # or: pip install stackwrench
stackwrench devcontainer --version      # prints the bare stackwrench version

# Or run without installing:
uvx stackwrench devcontainer --help
```

`python -m stackwrench devcontainer` is equivalent to `stackwrench devcontainer`.
There are no subcommands:

```text
usage: stackwrench devcontainer --config FILE --workspace ROOT [--json | --sarif] [--explain] [--strict]
  --json              Full wiring graph and diagnostics as JSON
  --sarif             SARIF 2.1.0 diagnostics for editors/CI (exclusive with --json)
  --compose-json FILE  Explicit pre-rendered Compose JSON (no merge is performed)
  --compose-base DIR   Base for relative Compose paths (default: first raw file dir)
  --daemon local|remote  Bind availability scope (default: local shared-filesystem assumption)
  --strict            Fail on warnings/unknowns as well as errors
  --explain           Show field locations, path bases, wiring targets and reasons
```

Every invocation is offline.

## Executable examples

Run these from the root of a stackwrench source checkout:

```sh
# Raw Compose YAML referenced by JSONC with comments and trailing commas; exit 0.
stackwrench devcontainer --config examples/devcontainer/.devcontainer/devcontainer.json --workspace examples/devcontainer --json --strict

# Image mode, explicit workspace mount and supported variable substitutions; exit 0.
stackwrench devcontainer --config examples/devcontainer/.devcontainer/image.json --workspace examples/devcontainer --strict

# Dockerfile mode; only file paths are inspected, nothing is built; exit 0.
stackwrench devcontainer --config examples/devcontainer/.devcontainer/build.json --workspace examples/devcontainer --strict

# Explain each path base, service reference, mount target and workspace mapping.
stackwrench devcontainer --config examples/devcontainer/.devcontainer/build.json --workspace examples/devcontainer --explain --strict

# Ordered overrides with an explicitly supplied final Compose JSON snapshot; exit 0.
stackwrench devcontainer --config examples/devcontainer/.devcontainer/overrides.json --workspace examples/devcontainer --compose-json examples/devcontainer/compose.rendered.json --json --strict

# The same raw files without a final model are deliberately rejected; expect 1.
stackwrench devcontainer --config examples/devcontainer/.devcontainer/overrides.json --workspace examples/devcontainer --json

# Missing service reference, with config and Compose locations; expect 1.
stackwrench devcontainer --config examples/devcontainer/.devcontainer/missing-service.json --workspace examples/devcontainer --json

# The same findings as SARIF 2.1.0 for editors/CI; expect 1 and a valid SARIF log.
stackwrench devcontainer --config examples/devcontainer/.devcontainer/missing-service.json --workspace examples/devcontainer --sarif

# Missing local bind source; expect 1, even if Compose might create the directory.
stackwrench devcontainer --config examples/devcontainer/.devcontainer/missing-source.json --workspace examples/devcontainer --json

# Local absence does not prove remote daemon absence: partial report, exit 0.
stackwrench devcontainer --config examples/devcontainer/.devcontainer/missing-source.json --workspace examples/devcontainer --daemon remote --json
```

All examples are synthetic. `compose.rendered.json` is a hand-authored final-model
fixture showing the `/work` mount replacement by target while retaining `/deps`;
it is not claimed to have been generated by Docker on this machine. These success
and failure examples are replayed by the test suite, which asserts their exit codes.

For your own ordered files, supply a reviewed final model. An optional manual
parsing command is `docker compose -f FIRST -f SECOND config --format json`; it
is never invoked by this tool and does not start containers. Review the rendering
environment and `.env` inputs yourself. Raw references must still exist as regular
files inside the declared root, but their contents are not parsed when
`--compose-json` is supplied. Original override provenance cannot be reconstructed
from the final JSON; locations refer to that JSON. Relative final-model paths use
the first referenced Compose file's directory, or explicit `--compose-base DIR`,
not the JSON snapshot's directory. Absolute paths must remain inside `--workspace`.

## Input scope and path rules

- Config: JSONC parsed by a port of jsonc-parser 3.3.1, including comments and trailing commas.
  Duplicate keys, malformed data and non-object roots are errors. Exactly one
  mode: `image`, `build`, legacy `dockerFile`, or `dockerComposeFile`.
- Image/Dockerfile: `build.dockerfile` is required with `build`; it and
  `build.context` (default `.`) are relative to the config directory, independently.
  Legacy `dockerFile` and `context` use the same base. Only local directory contexts
  and regular Dockerfiles are checked; their contents are not parsed.
- Compose: one plain YAML 1.2 or JSON file, or explicit strict pre-rendered JSON.
  No implicit override discovery, raw merge, YAML anchors/aliases/merge keys/tags,
  `include`, or `extends`. String and object builds are supported. Contexts are
  relative to the Compose base; Dockerfiles are relative to the build context,
  with `Dockerfile` as the default. `dockerfile_inline` and `additional_contexts`
  are rejected.
- `service` and every `runServices` entry must refer to a defined service. Every
  service definition's build inputs and mounts are checked, even with profiles or
  if omitted from runServices. Startup/dependency/profile activation is not simulated.
- Compose `depends_on` supports only the short string-list form, including `[]`.
  Each item must be a nonempty string without NUL or unresolved dollar expansion
  and must exactly match a defined service name; no trimming or substitution is
  performed. All definitions count, including services excluded by profiles or
  runServices. Repeated and self references are retained in occurrence order.
  Long-form mappings remain explicitly unevaluated, including their conditions;
  scalar/null fields are errors. No activation, dependency ordering, cycle
  analysis, health, conditions or runtime readiness is inferred.
- Dev Container `mounts` accept objects or Docker `--mount` strings;
  `workspaceMount` accepts a string in image/Dockerfile mode and needs
  `workspaceFolder`. Relative Dev Container bind sources use the declared workspace
  root, a checker convention; Compose bind sources use the Compose base.
- Supported mount types are bind, volume and tmpfs. Compose short volume syntax
  supports named, anonymous and Linux relative/absolute bind sources; long syntax
  requires `type` and `target`. Read-only and common consistency/SELinux flags are
  accepted but permission/label behavior is not assessed. Unknown options, volume
  subpaths, nondefault propagation and duplicate targets are errors.
  Separate Compose `tmpfs`, `configs`, `secrets`, `volumes_from` and `develop` fields
  are rejected because they can alter the analyzed mount graph; use the supported
  explicit volume representation where semantically equivalent.
- Named volumes are not host paths. Compose named references require top-level
  declarations. External/custom volume options produce an explicit runtime-unknown
  warning. Volume contents, population, drivers and permissions are not inspected.
- Container paths require absolute POSIX paths, normalized by segments. The longest
  covering mount wins; `/work` does not cover `/worker`. Under a bind, the mapped
  workspace subdirectory must exist and be a directory on the local snapshot.
  Missing coverage or coverage by volume/tmpfs yields a warning, since image or
  volume contents are unknown. Implicit workspace/Git-root mounts are not guessed.
  Trailing slashes are removed except for root `/`: `/work/src/` and `/work/src`
  select the same mount and conflict as duplicate targets. A nested volume at
  `/work/src/` hides a parent bind at `/work`, so workspace `/work/src` has unknown
  contents and fails `--strict` with `workspace-content-unknown`.
- Only `${localWorkspaceFolder}` and `${localWorkspaceFolderBasename}` expand in
  evaluated Dev Container wiring fields. No environment is read. Dollar expansion
  in Compose wiring must already be resolved. Unknown substitutions are errors in
  evaluated fields; other fields are listed as unevaluated, without expansion.
- The supplied workspace is both the local-workspace variable and the permitted
  host root. Config, Compose files, snapshot, contexts, Dockerfiles, bind sources
  and mapped directories must remain inside it, including symlink resolution.
  A deliberately broader `--workspace` root permits wider access, and also changes
  those two local-workspace substitutions. Symlink paths use their physical base.
  Tilde expansion, remote contexts, Windows paths, unresolved dollar characters
  and NUL are rejected. Mount strings cannot quote embedded commas/colons; use
  long-form objects for filenames needing delimiters. Documents are limited to
  2 MiB and 100 nesting levels.

## Reports and exit codes

`--json` writes one JSON object to stdout. Schema version 1 includes:

- `scope`: physical workspace root, local/remote daemon assumption, Compose base
  and ordered references, plus final-model provenance limitations.
- `nodes`: stable IDs within a report, source locations, host observations,
  resolved mount type/source/target, referenced services and workspace paths.
  Validated mount nodes retain their enclosing declaration location and include
  `sourceLocation` (null for anonymous mounts) and `targetLocation`.
- `edges`: source/destination IDs, relation, severity and resolved/invalid/unknown
  status. A missing-service edge points from config.service to Compose services.
  Declared `depends-on` edges connect the owning service to the referenced service
  and add the dependency occurrence's `location`. A missing dependency instead
  connects to `/services` with invalid status; its `missing-service` diagnostic
  edge starts at the individual reference node. Dependency reference nodes carry
  the owning `service` and validated `dependency` name. Edges are declarations,
  not an activation plan; repeated declarations keep separate occurrence locations.
- `diagnostics`: code, severity, message, endpoints when applicable, locations and
  host assumption. Line/column are 1-based; host-path locations have null line/column.
  A default or absent field has `inferred: true` and its nearest parent's location.
  Unreadable, non-file or oversized documents have null line/column, since their
  contents were not read; parser errors retain actual parser coordinates.
- `explanations`: reached path, mount, service-reference and workspace-coverage
  checks, available from the library and in every JSON report. Each has a source
  `location`, `relation`, physical resolution `base` (or null when inapplicable or
  unavailable), owning/referenced `service` when applicable, `target`, optional
  `targetLocation`, `status`, and `reasons` with codes and messages. Status is
  `resolved`, `invalid`, `unknown`, or `not-evaluated`. A resolved mount declaration
  does not establish its contents; workspace coverage is a separate check.
- `unevaluatedFields`: locations of each remaining subtree outside the wiring
  subset (e.g. lifecycle hooks, environment, image settings, labels, build args).
  These fields are neither dropped silently nor claimed to be validated. Reports
  do not dump their values. `runArgs`/`build.options` explicitly warn that they can
  alter path behavior.

`status: ok` means no errors/warnings in this subset, not full configuration
compatibility. `partial` means there are warnings/unknowns; `error` means a check
failed or input was rejected. Exit 0 permits warnings, exit 1 means errors (or any
warnings with `--strict`), exit 2 means CLI misuse or an unexpected internal error.
Text mode includes diagnostics and the host assumption; JSON adds the full graph.

`--sarif` writes one SARIF 2.1.0 log to stdout for editor and CI consumers. It is
exclusive with `--json` (combining them is CLI misuse, exit 2 with empty stdout).
Checks, diagnostic order/count and exit policy are identical to text/JSON mode:
every diagnostic becomes exactly one result, including repeated instances of a
rule. Errors retain level `error`, unknowns/warnings retain `warning`, and a clean
check produces an empty `results` array. `--strict` changes the exit policy only.
`--explain --sarif` still emits only the SARIF log; explanation/graph details are
available through `--json`. The default text output remains the default.

Rule IDs are the existing diagnostic codes, such as `missing-service` and
`missing-host-path`; they do not include filenames or array indices. Each result
has at most one primary `locations` entry, with other diagnostic endpoints in
`relatedLocations`. For example, `service: "absent"` in a Dev Container config
referencing a Compose file with only service `web` produces `missing-service`:
the primary location is config `/service`, and the related location is Compose
`/services`. Both carry the same 1-based source coordinates as JSON diagnostics.
Paths with spaces, `#`, `%` or Unicode are URI-encoded, relative to the physical
workspace under `uriBaseId: "%SRCROOT%"`; `originalUriBaseIds` records that root's
file URI. Columns use UTF-16 code units, as declared by `columnKind`.

Location properties preserve `jsonPointer` and, when applicable, `inferred: true`.
SARIF omits `region` for host-path observations, unread documents and inferred
fields whose nearest parent is known but whose own token does not exist. Failures
with no source location (for example, a missing workspace root) omit `locations`;
they are still results and still fail. Supplied final Compose JSON keeps locations
in that snapshot, without claiming original override provenance. Object mount
path errors use `/source` or `/target` as the primary location, with the exact
value token coordinates. Missing required fields retain their child pointer with
`inferred: true` and no SARIF region. String mounts keep their enclosing scalar
location, including `workspaceMount` and short-syntax Compose volumes. SARIF adds
no source text, environment dumps or unevaluated field values. It forwards existing
diagnostic messages and evaluated paths; the checker never reads environment
variables. Review the reported paths and messages before sharing reports.

The complete log is validated in tests against the unmodified OASIS schema at
[`a560296ca8c921f3bdb8d4a8db57ab83dae968a7`](https://github.com/oasis-tcs/sarif-spec/blob/a560296ca8c921f3bdb8d4a8db57ab83dae968a7/sarif-2.1/schema/sarif-schema-2.1.0.json).
The schema, hash and upstream terms are retained under `tests/devcontainer/fixtures/sarif/`;
validation runs offline and those test fixtures are not part of the installed package.
No editor extension, hosted code-scanning upload or Docker runtime was exercised.

Add `--explain` to text mode to see the explanation records and the locations of
fields outside wiring scope. With `--json --explain`, stdout remains one JSON
object; the flag does not change checks or exit policy. For example, a config in
`<root>/.devcontainer/devcontainer.json` with
`"build": { "context": "../src", "dockerfile": "Dockerfile" }` resolves both
fields independently from `<root>/.devcontainer`. The context entry shows:

```text
resolved [build-context] <root>/.devcontainer/devcontainer.json:LINE:COLUMN#/build/context
  base: <root>/.devcontainer
  target: <root>/src
```

`<root>`, `LINE` and `COLUMN` above stand for the physical workspace and actual
source coordinates. A missing directory instead shows `invalid`, its resolved
target and `reason [missing-host-path]`, with exit 1. An escaping context shows
`reason [path-escape]` at the context field with its base and rejected path in the
reason. An unresolved Compose context leaves the Dockerfile base unavailable and
marks that check `not-evaluated`. Compose Dockerfiles otherwise resolve from the
context; Compose bind sources resolve from the Compose base. `workspaceMount`
shows its config location, workspace-root base, source and normalized target.
`--explain` on `examples/devcontainer/.devcontainer/missing-service.json` identifies `/service`
and the Compose `/services` declaration, reports `missing-service`, and exits 1.

For example, with Dev Container `service: web`, this Compose YAML:

```yaml
services:
  web:
    depends_on: [db, missing]
  db: {}
```

produces a resolved declared `depends-on` edge `web` to `db` at
`/services/web/depends_on/0`, line 3, column 18, and `missing-service` at
`/services/web/depends_on/1`, line 3, column 22. `/services` at line 2, column 3
is related evidence. The missing reference exits 1 normally and with `--strict`.
JSON, text `--explain` and SARIF diagnostics use the same locations. Per-item
`depends-on` explanations identify the owning service, referenced definition
(or `/services`), null base and resolved/invalid outcome. An empty list has a
resolved explanation and no dependency edges; an absent field adds nothing.
Malformed list items report `invalid-field` at their own tokens, unresolved
dollar expansion reports `unsupported-substitution`, and later items still get
checked. Non-list scalars/null report `invalid-depends-on` at the field itself.
Long-form objects stay in `unevaluatedFields` and have a `not-evaluated`
explanation; they do not change the existing exit policy. Dependencies are checked
after each service's existing build/mount checks and cannot suppress those checks.
With `--compose-json`, all dependency evidence refers to the supplied strict
snapshot; original override locations are unavailable. SARIF exports diagnostics,
while declared edges and explanations remain available in JSON.

Rejected Compose `build` declarations identify their supplied value token:

```yaml
services:
  web:
    build: null
    volumes: [".:/work"]
```

With Dev Container `service: web` and `workspaceFolder: /work`, this exits 1 with
`invalid-build` (`build must be an object (or a Compose context string)`) at
`/services/web/build`, line 3, column 12. JSON's primary location and `from` build
node, text `--explain` diagnostics and SARIF's primary region agree. Booleans,
numbers and arrays are also rejected at their value tokens, without checking
array contents as build paths. The service declaration remains in the graph.
Mounts, workspace coverage, independent `depends_on` checks and later services
still get checked. Omitted builds, accepted context strings/objects and default
Dockerfile resolution retain their behavior. Earlier unsupported service wiring,
host-path evidence and Dev Container build handling retain their existing rules.
Raw strict JSON and supplied final JSON identify
their own value tokens; snapshots cannot recover original override provenance.

Rejected Compose object build fields also identify their own supplied values:

```yaml
services:
  web:
    build:
      context: .
      dockerfile_inline: "FROM scratch"
    volumes: [".:/work"]
```

This exits 1 with `unsupported-build` (`dockerfile_inline is not evaluated; use a
local Dockerfile`) at `/services/web/build/dockerfile_inline`, line 5, column 26.
`additional_contexts` is likewise rejected at its value token with
`additional_contexts is not evaluated`. This applies to every supplied value,
including null, false, empty strings, arrays and objects; neither field's contents
are evaluated. JSON's primary location and `from` field node, text `--explain`
diagnostics and SARIF's primary region agree in YAML, raw strict JSON and supplied
final JSON. Service and build nodes remain available in the graph. Context checks
still run first, and `dockerfile_inline` is rejected before `additional_contexts`
when both are supplied, regardless of key order. Rejection skips Dockerfile
resolution and continues mounts, workspace coverage, independent dependencies and
later services. Dev Container object build handling retains its existing evidence.

Rejected non-object Dev Container `build` declarations also identify their exact
supplied JSONC value token. For example:

```json
{
  "build": null,
  "workspaceFolder": "/work",
  "mounts": ["type=bind,source=.,target=/work"]
}
```

This exits 1 with `invalid-build` (`build must be an object (or a Compose context
string)`) at `/build`, line 2, column 12. JSON's primary location and `from` build
node, text `--explain` diagnostics and SARIF's primary region agree. Null,
booleans, numbers, arrays and strings (including empty strings) remain rejected;
array contents and strings are not evaluated as build paths or substitutions.
The document and build nodes remain in the graph. Independent mounts and
workspace coverage still run after the build error; strict mode also exits 1.
Accepted object builds, required `build.dockerfile`, object-build error evidence,
independent config-relative context/Dockerfile paths and legacy `dockerFile`
handling retain their existing behavior. Compose string builds remain supported.

Invalid Compose service `volumes` collections identify the supplied collection
value, rather than the owning service. For example:

```yaml
services:
  web:
    volumes: null
```

With Dev Container `service: web`, this exits 1 with `invalid-mount` and
`mounts/volumes must be an array`. JSON's primary location and `from` field node,
text `--explain` diagnostics and SARIF's primary region all identify
`/services/web/volumes` at line 3, column 14. Non-array scalars and objects are
also rejected at their own value tokens; their contents are not parsed as mounts.
The service declaration node remains available in the graph. Omitted collections
and empty arrays are accepted, with workspace coverage checked independently.
Earlier service unsupported/build checks retain their order and evidence;
`depends_on` and later services still get checked after collection failures.
Individual array mounts retain their field/scalar locations. Supplied strict
JSON uses its own collection token, without claiming raw override provenance.
Dev Container `mounts` handling is unchanged. Collection rejection occurs before
individual mount explanations; text diagnostics still show the exact failure.

For object mounts, `bind-source` (or `compose-bind-source`) explanations point
at `/source`, and `mount-target` points at `/target`. For example, the long-syntax
mount in `examples/devcontainer/compose.yaml` produces separate
`/services/web/volumes/0/source` and `/services/web/volumes/0/target` locations.
Changing its source to `./absent` produces `missing-host-path` at the source value
and exits 1; changing its target to `relative` produces `invalid-container-path`
at the target value and exits 1. Dev Container `mounts` objects use the same rule
at `/mounts/INDEX/source` and `/mounts/INDEX/target`. Workspace coverage identifies
the covering target token; duplicate-target errors identify the later target.
String mounts keep the original scalar location for both checks. Unsupported
object options also identify their exact value tokens. Nested Compose option structural failures identify the supplied `bind`, `volume`
or `tmpfs` group value token, including null, arrays and groups on the wrong
mount type. The mount node keeps its enclosing declaration identity.

For example, this rejected group value:

```yaml
services:
  web:
    volumes:
      - type: volume
        source: cache
        target: /work
        volume: null
volumes:
  cache: {}
```

still reports `invalid-mount`, `volume options require type=volume and an object`,
and exit 1, with primary `/services/web/volumes/0/volume` at line 7, column 17.
JSON diagnostic/field node, text `--explain` diagnostic and SARIF agree. For a
wrong-type group containing a block YAML mapping, its value starts at the first
nested key; flow mappings and supplied strict JSON point at the opening `{`.
With `--compose-json`, all evidence stays in the supplied final snapshot.
Expansion, top-level unknown/read_only/consistency checks and fixed
`bind`, `volume`, `tmpfs` traversal retain their order. Group structure still
precedes nested option checks; subpath still precedes nocopy. Scalar mount and
standalone parser calls without matching metadata retain enclosing fallback.
No additional options or group values are accepted.

Unknown object mount options remain errors with `invalid-mount` and exit 1.
The primary diagnostic, field node, text `--explain` diagnostic and SARIF all use
the offending value token. For example, with `service: web`:

```yaml
services:
  web:
    volumes:
      - type: volume
        source: cache
        target: /work
        volume:
          mystery: true
volumes:
  cache: {}
```

`Unsupported mount option mystery` points to
`/services/web/volumes/0/volume/mystery`, line 8, column 20. Top-level Compose
options, Dev Container object `mounts` options and nested Compose `bind`, `volume`
and `tmpfs` options follow the same rule. JSON pointers escape `~` and `/` in
keys; a supplied strict JSON snapshot uses its own value coordinates. Mount nodes
retain their enclosing declaration identity. No unknown option becomes accepted,
including false, null, empty, list or object values. Earlier top-level string
expansion checks still run first (so an empty string there remains `invalid-field`).
The first unknown follows JavaScript own-key iteration order (reproduced by the port), including numeric
keys; nested groups retain bind/volume/tmpfs validation order. Earlier read_only,
consistency and structural checks, and subpath-before-nocopy policy, are unchanged.
String mounts retain enclosing scalar evidence. Standalone mount parsers without
field metadata retain enclosing-location fallback.

Invalid object mount types use the exact `/type` value token in JSON diagnostics,
text `--explain` diagnostics and SARIF. For example, in this Dev Container input:

```json
{
  "image": "synthetic:example",
  "workspaceFolder": "/work",
  "mounts": [
    {
      "type": "unsupported",
      "source": ".",
      "target": "/work"
    }
  ]
}
```

`invalid-mount` exits 1 at `/mounts/0/type`, line 6, column 15. Compose long syntax
and supplied final JSON use their own `/services/SERVICE/volumes/INDEX/type`
token. An omitted type uses that child pointer with `inferred: true` and no SARIF
region. Non-string types keep the same `invalid-mount` verdict; an empty type
keeps the existing `invalid-field` verdict. The mount-target explanation records
the invalid outcome, and rejected types never reach bind-source host checks.
String mounts, including `workspaceMount`, retain their enclosing scalar location.
Supported bind, volume and tmpfs types retain their existing behavior.

Invalid object `read_only` values also use their exact field token. For example:

```json
{
  "image": "synthetic:example",
  "workspaceFolder": "/work",
  "mounts": [
    {
      "type": "bind",
      "source": ".",
      "target": "/work",
      "read_only": "invalid"
    }
  ]
}
```

This exits 1 with `invalid-mount` at `/mounts/0/read_only`, line 9, column 20,
in JSON, text `--explain` diagnostics and SARIF. Compose YAML long syntax and
supplied final JSON use their own `/services/SERVICE/volumes/INDEX/read_only`
value token. Dev Container objects accept booleans and the strings `"true"` and
`"false"`; Compose objects accept booleans only. Omission is accepted; an empty
string retains `invalid-field` at the same field. Invalid values stop later
target/path and bind-source host checks. String mount options, including the
`readonly` alias and `workspaceMount`, keep their enclosing scalar location;
Compose short mounts retain their existing `ro`/`rw` option policy.

Invalid object `consistency` values use the same exact-field rule. For example,
replace `"read_only": "invalid"` in the example above with
`"consistency": "invalid"`. The result is exit 1 with `invalid-mount` and
`Unsupported consistency value` at `/mounts/0/consistency`, line 9, column 22.
Compose long YAML and supplied final JSON use their own
`/services/SERVICE/volumes/INDEX/consistency` value token. JSON diagnostics, text
`--explain` diagnostics and SARIF agree; snapshot locations refer to the supplied
JSON, without claiming original override provenance.

In all three object formats, `"consistent"`, `"cached"`, `"delegated"` and omission
remain accepted; permission/cache behavior is not assessed. Other strings,
booleans, numbers, null, arrays and objects are rejected. An empty string retains
`invalid-field` at its own token. Rejected values stop later target/path and bind
host checks. Dev Container mount strings and `workspaceMount` keep their scalar
locations, as do Compose short mounts with invalid options. Accepted Compose
short flags `consistent`, `cached` and `delegated` retain their existing policy.

Invalid nested Compose `bind.propagation` values identify their own token too:

```yaml
services:
  web:
    volumes:
      - type: bind
        source: .
        target: /work
        bind:
          propagation: shared
```

This exits 1 with `invalid-mount` (`Only default rprivate bind propagation is

JSON diagnostic endpoints, text `--explain` diagnostics and SARIF agree. Supplied
final JSON uses its own nested value token, without claiming raw override
provenance. Only `rprivate` and omission are accepted; unsupported strings,
non-string values and the empty string retain `invalid-mount`. Nested options
are not expanded, so the empty string here differs from top-level empty string
options. Rejection precedes target/path and bind-host checks. Earlier
`read_only`/`consistency` failures, bind option object/type requirements, other
nested option rules and short mount scalar locations retain their existing policy.

Invalid nested Compose `bind.create_host_path` values also identify their own
value token. In the YAML above, replace `propagation: shared` with
`create_host_path: 42`. This exits 1 with `invalid-mount`
(`create_host_path must be boolean`) at
`/services/web/volumes/0/bind/create_host_path`, line 8, column 29. JSON diagnostic

## Library

The subpackage exports synchronous read-only `check` and `to_sarif` (also available
as `toSarif`) functions. Options use the same names as the JSON/JavaScript API:

```python
from stackwrench.devcontainer import check, to_sarif

report = check({
    "config": "examples/devcontainer/.devcontainer/devcontainer.json",
    "workspace": "examples/devcontainer",
    "daemon": "local",
    # "composeJson": "examples/devcontainer/compose.rendered.json",
    # "composeBase": "examples/devcontainer",
})
print(report["status"], report["summary"])
sarif_log = to_sarif(report)  # Pure conversion; no repeated checks or file reads.
```

`compose_json=` and `compose_base=` keyword arguments are accepted as aliases.
Paths supplied as options are relative to the invoking process's current
directory. Missing `config`/`workspace` or an unknown `daemon` raise `TypeError`;
input/configuration failures appear in the report. `dev_mount` and `compose_mount`
expose the standalone mount parsers, which raise `InputError` (with `code`,
`message` and `location`).

## Upstream relationship and limits

[decolint](https://github.com/bare-devcontainer/decolint) already lints Dev Container
files. The [Dev Container CLI](https://github.com/devcontainers/cli) resolves
configurations, and Docker Compose resolves its own model. This command focuses on
an offline cross-file graph and explicit host-path assumptions; it does not claim
these checks are universally absent upstream. [CLI issue #1026](https://github.com/devcontainers/cli/issues/1026)
is a closed runtime report, not proof that static checks can detect every bind failure.

The supported formats follow the [Dev Container reference](https://github.com/devcontainers/spec/blob/main/docs/specs/devcontainerjson-reference.md)
and [Compose specification](https://github.com/compose-spec/compose-spec). The JSONC
parser is a Python port of Microsoft's MIT-licensed jsonc-parser 3.3.1, and YAML
behaviour follows the ISC-licensed npm `yaml` 2.9.1 package; see [THIRD_PARTY.md](../THIRD_PARTY.md)
and [licenses/devcontainer](../licenses/devcontainer/). No GPL podman-compose or MPL ComposeLens
implementation was copied.

The test suite runs actual CLI processes and covers source mapping, supported
format conversions, filesystem failures, strict unknown handling and
nonexecution of hooks. No performance or container-runtime compatibility claims
are made.
